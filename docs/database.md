# Database Design

SQLite for local development, via SQLAlchemy ORM. Every table uses a 32-character hex UUID
primary key (`app.models.base.gen_uuid`) rather than an auto-increment integer, so IDs are
non-guessable (a small extra defense against IDOR probing) and safe to expose in URLs.
Switching to PostgreSQL in production is a one-line change (`DATABASE_URL` in `.env`) - no
application code references SQLite-specific behaviour.

## Entity overview

```
Organization 1---* User
Organization 1---* Mailbox
Organization 1---* DetectionRule (custom rules)
Organization 1---* WhitelistEntry / BlacklistEntry
Organization 1---* AuditLog

Mailbox 1---* Email
Mailbox 1---* ScanJob

Email 1---* Attachment
Email 1---* URLRecord
Email 1---1 ThreatAnalysis
Email 1---1 QuarantineItem (nullable - only when quarantined)
Email 1---* Feedback

ThreatAnalysis 1---* ThreatIndicator

DetectionRule 1---* RuleCondition

User 1---* UserSetting
User 1---* Notification
```

## Key tables

| Model | Purpose |
|---|---|
| `Organization` | Tenant boundary; every other org-scoped row references this. |
| `User` | Auth identity, role (`admin`/`user`), belongs to exactly one organization. |
| `Mailbox` | A connected mailbox: provider type, encrypted credentials/OAuth token, monitoring settings, running counters. |
| `Email` | One row per uniquely-deduplicated message: envelope fields, body, classification, threat score, status, action taken. |
| `Attachment` / `URLRecord` | Extracted attachment/URL metadata per email (never raw executable content). |
| `ThreatAnalysis` | Per-category score breakdown + total + classification for one email (1:1 with `Email`). |
| `ThreatIndicator` | One row per triggered rule for a `ThreatAnalysis` - this *is* the explainability record. |
| `DetectionRule` / `RuleCondition` | Custom rules created via the Rule Builder (built-in rules live in code, not the DB). |
| `WhitelistEntry` / `BlacklistEntry` | Per-organization trusted/blocked emails or domains. |
| `QuarantineItem` | Quarantine state machine for one email (quarantined -> released/marked_safe/deleted). |
| `ScanJob` | One row per scan run, with per-classification counters - powers Scan History. |
| `AuditLog` | Append-only security/activity audit trail. |
| `Notification` | In-app user notifications generated by the policy engine. |
| `UserSetting` / `SystemSetting` | Per-user preferences and global, editable configuration (thresholds, action policy, branding, retention). |
| `Feedback` | False-positive / false-negative reports tied to an email, for rule-tuning research. |

## Indexing and constraints

- `Email.dedup_key` has a unique constraint scoped to `(mailbox_id, dedup_key)` - this is what
  makes rescans idempotent (Section 53).
- `Email.mailbox_id` + `Email.classification` has a composite index for dashboard/report
  aggregation queries.
- `Email.sender` and `Email.sender_domain` are indexed for the top-senders/top-domains
  reporting queries and for the sender search filter.
- `WhitelistEntry`/`BlacklistEntry` enforce a unique `(organization_id, value)` constraint so
  the same address/domain can't be added twice per organization.
- Every model uses `created_at`/`updated_at` timestamps (`TimestampMixin`).

## Why credentials are not modeled as plain columns

`Mailbox.encrypted_password` and `Mailbox.encrypted_oauth_token` store Fernet-encrypted
ciphertext, never plaintext. Decryption happens exclusively inside
`app/services/mailbox_service.py` (`get_decrypted_password` / `get_decrypted_oauth_token`),
immediately before handing credentials to a provider instance - no other module in the
codebase touches these columns.
